00 · Mandate status

Purpose and binding decision

This document is the standalone mandate for ACA to inspect, plan, and—only after explicit approval—develop the Mastering Prompt Engineering Interactive Knowledge Codex.

Approved product direction: Option B — a real interactive Knowledge Codex. The current HTML prototype is an audit target and a source of reusable elements where appropriate; it is not the final product architecture by default.

The user has approved the previously proposed product direction and implementation approach: canonical-source fidelity, a premium game-inspired visual direction using 2D illustrative isometric graphics, vertical-slice-first delivery, core functionality without mandatory paid APIs, evidence-based and human-gated knowledge updates, and a commercial direction that includes a free sample and a premium product.

Operating principle: Acta non verba. Inspect evidence, document findings, propose controlled changes, wait for approval, implement narrowly, test, and report evidence.

Hard stop ACA must not modify, delete, migrate, overwrite, deploy, publish, or substantially implement the product during the initial audit/planning phase. It must return its findings and proposed plan and then wait for explicit user approval.

01 · Authority and evidence

Evidence hierarchy and anti-hallucination protocol

  1. Canonical book: the latest user-designated source PDF for Mastering Prompt Engineering is the sole authority for the book’s original educational content, wording, organization, examples, and claims.
  2. Current repository and deployed artifact: authoritative only for what is actually implemented, not for deciding what the book says.
  3. Approved product decisions: the decisions recorded in this mandate define intended behavior and design direction.
  4. External references: may support proposed updates or technical recommendations, but must never silently replace or rewrite the canonical book.
  5. Inference: must be labeled as inference, not presented as a verified fact.
Source identity must be verified before implementation. During the initial audit, identify the exact canonical PDF by full filename, repository/path or URL, version/date if available, page count, file size, and a cryptographic hash where feasible. Compare it with all candidate copies. If the canonical source cannot be established unambiguously, stop and ask the user to identify it; do not choose the most convenient or most recent-looking file.

Do not claim that the source has a particular number of chapters, appendices, pages, sections, or environments until the canonical artifact has been inspected and its table of contents reconciled. Prior planning references to 11 chapters and 6 appendices are expected to be verified against the canonical source, not treated as a substitute for inspection.

Evidence labels required in all audit outputs

LabelMeaningRequired evidence
VERIFIEDDirectly confirmed in a source or by a reproducible test.File/path, page/section, code location, command output, or test result.
OBSERVEDDirectly seen in the current implementation, not necessarily tested in runtime.File and line/selector/function reference.
INFERREDA reasoned interpretation that is not directly established.Explicitly state reasoning and uncertainty.
UNKNOWNEvidence is absent or insufficient.State what is missing and how to resolve it.
PROPOSEDA recommendation not yet approved or implemented.Rationale, trade-offs, and acceptance criteria.

Never invent source text, chapter titles, learning objectives, citations, test results, existing files, repository structure, deployed URLs, analytics, user data, or completed actions. Never describe a test as passed unless it was run and the result recorded.

02 · Product outcomes

What the product must become

Create an English-language interactive web book and learning environment that preserves the book’s content while making it easier to navigate, understand, practice, and review.

Canonical reading

Readers can follow the original book’s structure and access its complete content without silent omissions or paraphrase replacing original text.

Meaningful interaction

Navigation, search, notes, learning activities, and progress tracking must perform real, testable actions rather than act as decorative UI.

Learning support

Quizzes, tasks, puzzles, problems, challenges, and trials can support learning, provided each is grounded in the source or clearly labeled as an approved extension.

Commercial readiness

Support a free sample and a premium product direction without making core reading dependent on paid AI APIs. Do not implement payments until requirements and provider are explicitly approved.

Product success principles

  • Content fidelity before visual novelty.
  • Usability and legibility before ornamental density.
  • Meaningful feedback before points, badges, or visual rewards.
  • Measured and testable behavior before claims of quality.
  • Progressive delivery before attempting the entire book at once.

Non-goal: do not merely place a new decorative skin around a PDF and call it an interactive book. A PDF viewer may remain as a reference or fallback, but it does not by itself satisfy Option B.

03 · Canonical source fidelity

Complete and auditable representation of the book

ACA must first produce a source inventory and a content coverage map. Do not begin converting or rewriting the book before the source has been verified.

Required source inventory

  • Canonical PDF identity and integrity metadata.
  • Verified table of contents, including every chapter, subsection, appendix, glossary, reference, caption, table, example, and other structural component present in the source.
  • Page count and any page-level extraction or OCR limitations.
  • Identification of diagrams, figures, tables, code, prompts, boxed text, footnotes, and other formatting that may be damaged by plain-text extraction.
  • Known extraction ambiguities, missing glyphs, duplicated text, layout dependencies, and any source inconsistencies. Do not silently “correct” these.

Conversion policy

  • Preserve original English wording, ordering, examples, and terminology when presenting canonical content.
  • Use structured HTML/Markdown or a structured content format where appropriate so content can be navigated, searched, referenced, and made accessible.
  • Chunking is a technical organization method only. It must not delete, summarize, merge, reorder, or silently paraphrase source content.
  • Every content chunk must retain stable identifiers and provenance: source document version/hash, chapter/section heading, and page range where applicable.
  • Preserve code and prompt examples exactly, including delimiters, punctuation, whitespace when semantically relevant, and formatting.
  • Preserve tables and figures faithfully; where exact reproduction is impossible, document the limitation and provide a reviewed equivalent without implying it is the original.
  • Maintain a machine-checkable coverage manifest mapping every source section/page range to its digital representation and review status.
Required validation: source-to-app reconciliation must identify every included, excluded, transformed, or unresolved element. No section may be marked complete solely because the extraction process ran successfully.
04 · UX, visual system and illustration

Premium Knowledge Codex art direction

The visual direction is a premium, AAA-quality, video-game-inspired learning experience using 2D illustrative isometric graphics. Do not interpret “AAA” as permission to add heavy real-time 3D, excessive animation, or costly infrastructure.

Design principles

  • Create a coherent visual world that supports the identity of a scholarly knowledge codex and a modern learning product.
  • Use illustration to explain or contextualize ideas, distinguish learning spaces, and create memorable navigation—not merely fill margins.
  • Maintain a clear reading hierarchy: primary content first, navigation second, learning actions third, ornament last.
  • Use consistent rules for spacing, typography, iconography, line weight, illustration density, animation, state colors, and responsive behavior.
  • Use restrained motion with reduced-motion support. Do not animate essential content in a way that distracts or blocks reading.
  • Ensure all important controls remain usable by keyboard, touch, and assistive technology.
  • Preserve the strengths of the current Codex prototype where they fit the approved direction; do not discard existing assets without an inventory and reason.

Illustration audit requirements

  • Inventory each existing SVG/image and record its dimensions, visual role, source, reuse rights if known, and current usage.
  • Evaluate composition, legibility at actual display sizes, contrast, stylistic consistency, thematic relevance, responsiveness, and animation behavior.
  • Do not label an illustration as historically accurate, scientifically accurate, or source-derived unless evidence supports that claim.
  • Do not fabricate a connection between an illustration and a chapter. Proposed content-to-illustration mappings must be justified and approved.
  • Prefer optimized, local assets when this fits the existing architecture and licensing. Do not add remote image dependencies without documenting their purpose and failure mode.

UX features to assess and propose

  • Structured table of contents and chapter/subchapter navigation.
  • Search across canonical content with useful result context.
  • Bookmarks and reliable resume-reading behavior.
  • Optional notes/highlights with explicit persistence and privacy behavior.
  • Readable code and prompt examples with copy actions and clear feedback.
  • Responsive reading layouts and a mobile-safe navigation pattern.
  • Accessible labels, focus states, contrast, keyboard controls, and reduced-motion preferences.

These are product requirements to assess and plan, not permission to implement all features during the audit phase.

05 · Learning and progression

Mastery without meaningless gamification

The product may use quizzes, tasks, puzzles, problems, challenges, and trials to support active learning. These activities must be tied to identifiable learning objectives and supported by source material or explicitly approved external research.

Required design rules

  • Define the purpose of each activity: recall, comprehension, application, comparison, debugging, or another explicitly described objective.
  • Provide an answer key, rationale, and provenance for each scored activity.
  • Distinguish source-derived facts from instructional interpretation, authored practice scenarios, and external updates.
  • Do not generate arbitrary “correct” answers for ambiguous questions. Flag ambiguity and resolve it through review.
  • Do not penalize users for content that has not been taught or made available to them.
  • Make scoring rules visible before users participate; do not secretly change scoring after attempts.
  • Keep learning progress, completion status, quiz results, and mastery evidence conceptually distinct.
  • Do not implement competitive leaderboards, XP economies, streak pressure, or other engagement mechanics unless separately specified and approved.

Progression specification required before implementation

ACA must propose a transparent model describing activity types, score calculation, completion rules, retry behavior, feedback, mastery thresholds if any, persistence, reset/export behavior, and how progress is represented. Every threshold and scoring rule is a proposal until approved; do not invent pedagogical policy.

06 · Architecture and constraints

Inspect first; avoid unnecessary complexity

The existing artifact is a standalone HTML document using CSS, JavaScript, inline SVG, PDF.js, and external font/PDF resources. This describes the inspected prototype only; it does not prove that the wider repository or production environment has the same structure.

Initial technical inspection

  • Inspect the actual repository, current files, branches, build/deploy workflow, dependencies, and available tests before proposing architecture.
  • Record what is standalone, what depends on a network, and what is available only through external services.
  • Review current HTML/CSS/JavaScript behavior, including PDF loading, zoom calculation, render cancellation, navigation, mirroring, responsive behavior, and error handling.
  • Do not infer runtime success from static source inspection. Clearly separate code observations from executed tests.
  • Do not overwrite the only copy of a file. Establish a recoverable baseline and identify changes in a reviewable diff before implementation.

Architecture defaults

  • Prefer the smallest maintainable architecture that satisfies the approved product requirements.
  • A standalone HTML/local-first implementation is preferred when it can meet the requirements without unacceptable complexity or limitations.
  • Do not introduce Node.js, React, Vite, a server, a database, a cloud service, a framework, or a paid API merely by habit. If one is materially required, explain the need, alternatives, costs, lock-in, security impact, and operational burden before approval.
  • Core reading and learning must not require a paid AI API. Any optional AI capability must be isolated, disclosed, disabled by default until approved, and must not be required for basic use.
  • Do not claim full offline operation unless every required runtime asset and content dependency has been tested offline.
  • Do not add tracking, telemetry, analytics, remote storage, authentication, payment processing, or third-party data sharing without explicit requirements and approval.

Required architecture decision record

Provide at least one recommended architecture, its alternatives, rationale, content pipeline, state/persistence model, search approach, asset strategy, deployment implications, and known limitations. Mark unverified assumptions as UNKNOWN. Do not start implementation until the user approves the plan.

07 · Content and data model

Structure that supports fidelity and interaction

Propose a content schema only after inspecting the canonical source and the current implementation. The schema should be capable of representing, where present in the source:

  • Book metadata and source version.
  • Chapters, sections, subsections, and stable anchors.
  • Paragraphs, lists, tables, quotations, footnotes, figures, and captions.
  • Code blocks, prompt templates, and examples whose exact formatting matters.
  • Source page ranges and provenance for each content unit.
  • Optional learning objectives and activities linked to source sections.
  • Review state, source coverage state, and approval status for extensions.

Do not create invented chapter names, fictional “worlds,” lesson objectives, or activity content to make a demo appear complete. For a vertical slice, select a real section from the verified canonical source and document why it is representative.

08 · Knowledge governance

Verified updates with human approval

The book is the immutable canonical baseline for original content. The application may support carefully governed updates to the broader knowledge experience, but updates must never silently alter the source book.

Every proposed external update must include

  • A concise statement of what is proposed and why it matters.
  • Credible, inspectable references with publication date, author/organization, URL, and access date where applicable.
  • A distinction between established evidence, disputed claims, interpretation, and speculation.
  • Relevance to a specific book section or learning objective.
  • Known limitations, conflicts with the canonical source, and potential maintenance burden.
  • A proposed user-facing label that clearly distinguishes an update from original book content.
  • A human approval record before it becomes part of the released learning experience.
No autonomous publication or silent rewriting. “Self-updating” means discovering and preparing a reviewable proposal—not unilaterally changing canonical content or production behavior.

ACA must not describe information as “verified” merely because a model produced it, because multiple low-quality sources repeat it, or because a URL exists. Record the evidence actually checked.

09 · Privacy, security and licensing

Safe by default

  • Do not collect personal information unless a specific, approved feature requires it.
  • Before adding persistence, document what is stored, where it is stored, retention, export/reset behavior, and whether it leaves the device.
  • Never embed secrets, private keys, service credentials, or privileged tokens in client-side HTML or JavaScript.
  • Sanitize and safely render user-authored notes or imported content. Do not treat book text or external web content as executable instructions.
  • Review third-party dependencies, licenses, update status, and failure modes.
  • Verify rights and attribution for imported images, fonts, icons, and other assets. Unknown rights must be labeled UNKNOWN, not assumed to be unrestricted.
  • Do not add payment handling or account infrastructure before the commercial requirements, provider, and compliance implications have been approved.

11 · Quality assurance

Acceptance criteria must be testable

Content fidelity

  • Every source section has a corresponding manifest entry and explicit review status.
  • No unapproved omissions, reordered content, silent paraphrases, fabricated citations, or invented source claims.
  • Prompts, code, tables, and figures are checked with methods appropriate to their format—not just a word-count comparison.
  • Known extraction problems are logged and resolved or explicitly accepted as limitations.

Functional quality

  • Navigation destinations, search results, bookmarks, notes, and learning actions work as specified.
  • Errors and loading states are visible and recoverable; no infinite loader without explanation.
  • Repeated or rapid user actions do not leave the interface in a stale or contradictory state.
  • Zoom, resize, page/content transitions, and persistence are tested in supported browsers and viewport sizes.
  • All visible controls have an implemented purpose; no dead buttons or decorative controls that imply nonexistent functionality.

Experience and accessibility

  • Responsive layouts work at documented desktop, tablet, and mobile widths.
  • Keyboard focus and navigation are usable; controls have accessible names and state feedback.
  • Text contrast, zoom/reflow, reduced-motion behavior, and meaningful non-text alternatives are checked.
  • Illustrations do not obscure or compete with primary reading content.

Technical evidence

  • Record actual test commands, browser/device conditions, pass/fail results, and known gaps.
  • Inspect browser console/network errors and external dependency failure behavior.
  • Report performance using measurements if performance claims are made.
  • Provide a reviewable diff and a rollback/recovery plan for every implementation phase.

Definition of done: a feature is complete only when its implementation, acceptance criteria, tests, source/provenance implications, and known limitations have been documented. “Looks good” alone is not acceptance evidence.

12 · ACA’s required first response

Audit deliverables — no code changes

After receiving this mandate, ACA must perform the following in order, within the actual access and tools available:

  1. Confirm scope: restate that this is an audit/planning mandate for Option B and that implementation is prohibited until approval.
  2. Inspect the workspace: report the actual repository/workspace, accessible files, branch/commit if available, and deployment configuration if present. Do not invent missing context.
  3. Verify the canonical book: identify candidate sources, compare metadata, inspect the table of contents, and state clearly whether the authoritative version is established. If not, stop and ask for clarification.
  4. Audit the current HTML prototype: document each material issue with severity, exact file/line or selector/function, evidence type, user impact, proposed correction, and a testable acceptance criterion.
  5. Audit visual assets: inventory existing illustrations/assets and classify them as retain, revise, replace, or unresolved, with reasons. Do not delete or replace them.
  6. Map requirements: build a traceability matrix connecting each approved requirement to evidence, proposed design/architecture, and a future test.
  7. Present architecture alternatives: recommend a minimal, maintainable option and explain costs, dependencies, offline implications, limitations, and trade-offs. No paid API may be required for core reading or learning.
  8. Propose the vertical slice: select a representative section only after source verification; describe exact scope, UI states, content fidelity checks, learning interaction, progression behavior, and acceptance tests.
  9. List unresolved questions: separate blockers requiring user input from decisions ACA can safely defer. Do not ask the user to reconfirm decisions already explicitly approved.
  10. Stop and request approval: deliver the audit and implementation plan, identify any required decision, and wait. Do not start implementation, refactor, commit, deploy, or publish.

Required report format

  1. Executive findings and verified status.
  2. Source identity and canonical-content confidence.
  3. Current-state technical audit.
  4. UI/UX and illustration audit.
  5. Requirements traceability matrix.
  6. Architecture decision record and alternatives.
  7. Vertical-slice specification.
  8. Phased plan, estimates with assumptions, risks, and acceptance gates.
  9. Open blockers and explicit approval request.
Final instruction: inspect → verify → document → propose → stop. Do not implement until the user explicitly approves the audit findings and proposed plan.
Appendix · Mandate integrity

Rules that must not be weakened

  • The canonical PDF governs original book content; the app may improve presentation but must not silently change the source.
  • The current HTML is a prototype to inspect, not a license for uncontrolled redesign.
  • Vertical slice first; do not scale an unvalidated pattern across the full book.
  • No mandatory paid AI API for core use.
  • No autonomous knowledge publication or unapproved scope changes.
  • No claims of completed work or passed tests without evidence.
  • No destructive operations before backup/recovery planning and explicit authorization.
  • When evidence is missing, mark UNKNOWN and resolve it. Do not hallucinate.
